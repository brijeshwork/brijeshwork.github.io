In Search Engine Optimization (SEO) and web analytics, tracking external backlinks pointing to a customer's website is vital for authority building, risk auditing, and competitor analysis. In this chapter, we design an enterprise-grade distributed Backlink Monitoring System capable of monitoring millions to 100 million active backlink edges continuously.

1. Understand the Problem & Scope

A backlink is a directed logical edge from a source URL (referring web page) to a target URL (monitored customer page). Designing a backlink monitoring system differs significantly from building a general web crawler: rather than recursively discovering the entire web graph, a backlink monitor performs targeted, scheduled revalidation of known edges, tracking state transitions over time.

Clarifying Questions & Scope Confirmation

Candidate: What is the core functionality of the backlink monitoring system?
Interviewer: The system allows customers to monitor backlinks pointing to their domains. It must detect state changes: New, Lost, Recovered, Redirected, NoFollow tag changes, or target page status changes (e.g., 404, 500, indexability).
Candidate: What scale are we targeting?
Interviewer: Design for a 10 million backlink baseline initially, with a clear architectural roadmap to scale up to 100 million backlink edges.
Candidate: How often should each backlink be verified?
Interviewer: Every eligible backlink edge should be checked at least once during a rolling 7-day window. Missing backlinks should be confirmed within 2 hours under normal load.
Candidate: How long should raw HTML and observation history be stored?
Interviewer: Transactional state stores current status and recent changes. Historical observation analytics follow the tenant's contractual retention policy and deletion obligations, while raw HTML content is deduplicated and normally expires after 30 days.

Functional & Non-Functional Requirements

Functional Requirements
  • Track durable availability states (UNKNOWN, LIVE, LOST) separately from transition events (NEW, LOST, RECOVERED) and link properties such as redirects.
  • Monitor anchor text, rel flags (nofollow, ugc, sponsored), and DOM location.
  • Support source and target HTTP evaluation, including X-Robots-Tag, the HTTP Link canonical relation, and HTML canonical elements.
  • Provide configurable multi-channel alert delivery (Email, Slack, Webhooks).
  • Support bulk candidate imports from third-party SEO data providers.
Non-Functional Requirements
  • High Efficiency: Shared fetching so one source URL is requested only once per window even if monitored by multiple projects.
  • Idempotency: No duplicate alerts or lost status transitions during worker retries or failures.
  • Low Dashboard Latency: Transactional queries for customer dashboards complete in < 50ms without scanning full history.
  • Politeness & Safety: Strict per-host crawling rate limits and obey robots.txt.

Bandwidth & Conditional GET Savings

Assuming an average compressed HTML response body of 250 KB per referring page:

  • Full-Body Transfer without caching: At 1M edges (625K URLs/week) = 156 GB / week; at 10M edges (6.25M URLs/week) = 1.56 TB / week; at 100M edges (62.5M URLs/week) = 15.6 TB / week.
  • With Conditional Headers (ETag / If-Modified-Since): Assuming a 70% 304 Not Modified rate across weekly recrawls, response-body bandwidth drops to approximately 47 GB / week at 1M edges, 469 GB / week at 10M edges, and 4.69 TB / week at 100M edges.

These are successful source-page body transfers only. Production capacity must separately budget for redirects, robots requests, confirmation and network retries, target-page checks, browser assets, object-storage traffic, Kafka replication, and CDC. Size workers and brokers from measured p95/p99 service time and maintain at least 2× recovery headroom over the forecast peak.

Storage Growth Math

  • Current Edge State (base-row floor): 1M edges = ~500 MB; 10M edges = ~5 GB; 100M edges = ~50 GB at 500 bytes per logical row. Capacity planning must add secondary indexes, URL/domain dictionaries, occurrences, jobs, rollups, free space, backups, and replica copies; validate the multiplier with production-shaped data.
  • Immutable Observations (ClickHouse planning baseline): 1M edges = 52M rows / year; 10M edges = 520M rows / year; 100M edges = 5.2B rows / year. Byte estimates must be benchmarked with real anchor-text and metadata distributions rather than treated as a fixed compression ratio.

3. High-Level Architecture

The system decouples network fetching, raw body storage, offline HTML parsing, project matching, and alert processing into separate asynchronous pipeline stages connected via message queues and an event backbone.

Pipeline Execution Stages

  1. Scheduler: Scans due projects and target source URLs, creating fetch tasks without creating duplicate network jobs.
  2. Fetch Coalescer: Groups pending checks by public source URL, ensuring multiple projects monitoring links on the same external page trigger only one HTTP request.
  3. Source Fetch Workers: Perform HTTP/HTTPS requests with conditional headers (If-None-Match, If-Modified-Since), handling redirects, timeouts, and rate limits. Save changed source bodies to Object Storage.
  4. Target Validation Workers: Coalesce distinct monitored target URLs into lightweight validation jobs that record status, redirect destination, canonical identity, and indexability. Target failures do not prove that a source backlink is missing.
  5. Offline Parsers: Parse DOM trees from stored HTML snapshots, extract outgoing anchor tags, canonical tags, meta directives, and write a light link manifest.
  6. Project Matchers: Compare extracted target links against target rules for subscribing projects. Calculate availability transitions (for example, LIVE ➔ LOST) and emit transition events separately.
  7. Transactional Outbox & CDC: Commit edge state changes into MySQL. An outbox worker emits notification events while MySQL Binlog CDC streams facts into ClickHouse.

4. Database Design & Storage Placement (Developer PRD Spec)

To deliver sub-50ms dashboard response times while maintaining complete historical audit trails, data is tier-placed across MySQL 8.0+ / Vitess (System of Record for current state and transactional queues), ClickHouse (Analytics engine for immutable observation history), and Object Storage (Raw compressed HTML snapshots). Identifiers use application-generated UUIDv7 stored as BINARY(16) for sequential primary key locality.

5. Cron, Scheduler & Worker Flow

Cron is strictly a lightweight trigger mechanism—it initiates job reservations and exits immediately. All scheduler instances route writes to the authoritative database primary; row locking and renewable leases prevent duplicate ownership across regions.

Step-by-Step Verification Cycle

Each verification run follows a deterministic 10-step pipeline. Every step is idempotent and safe to retry after a crash.

Step 1 — Trigger One Scheduler Slot

An external cron starts project_scheduler every minute. It rounds the current UTC time to the minute and inserts one row into scheduled_job_runs with job_name = 'project_scheduler' and scheduled_for = current minute. The winner records a short renewable lease. A competing instance exits only while that lease is valid; after expiry, a recovery instance atomically reclaims the same slot. This avoids a permanently stuck minute when the first process crashes.

Step 2 — Claim Due Projects

In a short transaction, select a small batch of active projects ordered by urgency. No network calls may occur while this transaction is open.

Step 3 — Create an Idempotent Crawl Run

For each locked project, calculate a deterministic run key, insert a crawl_runs row, and advance next_crawl_at before the same transaction commits. The unique key on idempotency_key makes uncertain retries harmless. Normally advance from the previous scheduled value; when it remains overdue, move it to one interval after the current time so recovery creates at most one catch-up run rather than an unbounded storm.

Run Idempotency Key Formula
run_key = SHA-256(project_id + ':verification:' + scheduled_slot)
Step 4 — Expand the Run into Unique Page Checks

The run expander groups backlinks due for verification by source URL. One source page linking to 50 monitored URLs generates only one page check. Each consumer records required_validated_after and validation_deadline. The coalescing key prevents two projects from triggering two HTTP fetches for the same source page.

Run Expansion Query
SELECT b.source_url_id, MAX(b.check_priority) AS priority
FROM backlinks AS b
WHERE b.project_id = ?
  AND b.next_check_at <= UTC_TIMESTAMP(6)
  AND EXISTS (
    SELECT 1
    FROM backlink_target_matches AS m
    JOIN project_targets AS t ON t.id = m.project_target_id
    WHERE m.backlink_id = b.id
      AND m.is_active = TRUE
      AND t.is_active = TRUE
      AND t.deleted_at IS NULL
  )
GROUP BY b.source_url_id
ORDER BY priority DESC;

HTTP 200 — New Body

Compress HTML, store in object storage, insert page_content_snapshots using SHA-256 body hash. Duplicate hash reuses existing snapshot — no second upload.

HTTP 304 — Not Modified

Create a new validation result referencing the previous snapshot. No HTML is downloaded or stored again. If referenced content is missing, retry once unconditionally.

Error / Non-HTML

Record metadata and failure policy. Never create an HTML snapshot. Retain previous live/lost state — a network error is not evidence of a missing backlink.

Target-Page Health Checks

Source verification and target health are independent signals. A target_validation_job is coalesced by normalized target URL and validation window, uses the same SSRF, redirect, timeout, robots-policy, and global per-host controls as source fetching, and never downloads a body unless canonical or indexability evaluation requires it. Its result populates target_http_status, final_target_url_id, target fetch health, and target indexability. A target outage may create a target-health event, but it cannot create a source-link lost transition.

Step 6 — Apply Safe Fetch Controls (SSRF Prevention)
  1. Permit only http and https schemes.
  2. Resolve DNS and reject loopback, private, link-local, metadata-service, and other forbidden IP ranges.
  3. Revalidate redirect destinations with the same SSRF rules.
  4. Apply robots.txt and product-policy rules.
  5. Acquire a per-host rate-limit token from Redis — global across all workers, not local to one process.
  6. Enforce connect timeout, response timeout, body-size limit, redirect-count limit, and total-time limit.
  7. Use a clear crawler user-agent string with a contact URL.
Browser Rendering Tier: Raw HTTP fetching is the default. Browser rendering is a separate quota-controlled fetch profile used only when project policy requests it or heuristics indicate JavaScript-rendered content is necessary. Browser workers run in a hardened sandbox with no tenant cookies. Downloaded HTML is data — never execute it in the ordinary parser process.
Step 7 — Parse the Stored Snapshot Offline

After a successful fetch, create or reuse page_parse_results identified by (content_snapshot_id, base_url_id, parser_version). The parser downloads the compressed object internally, extracts raw and resolved links, anchors, rel attributes, image-link status, placement, canonical data, and indexability, then writes a compact compressed link manifest back to object storage.

URL resolution base matters: Identical HTML served from two different URLs may contain relative links that resolve to different absolute targets — the base URL is part of the parse identity.

Truncation rule: Hitting body, decompression, parse-time, DOM-node, or extracted-link limits produces is_truncated = TRUE. A truncated result can confirm links that were found, but it can never prove that a previously known link is absent.

Step 8 — Record Observations Atomically

In one database transaction for one project consuming the parsed page, perform all of the following steps atomically:

  1. Upsert any newly encountered domains and URLs by their hashes.
  2. Upsert the logical backlinks edge using (project_id, source_url_id, target_url_id).
  3. Insert one immutable backlink_observations row per edge.
  4. Maintain backlink_target_matches for every active target definition matched by the edge.
  5. Update individual backlink_occurrences; the immutable link manifest remains the detailed historical evidence.
  6. Reference the source fetch job, optional target validation job, and parse result so every observation has reproducible evidence.
  7. Use an observation idempotency key: SHA-256(crawl_run_id + ':' + source_url_id + ':' + target_url_id).
  8. Update the current backlink row and next_check_at.
  9. Insert any alert event, its channel delivery rows, and required broker events in the transactional outbox.
  10. Mark the project-scoped crawl_pages consumer as completed. Then commit.
Idempotent Retries: If the worker retries after an uncertain database response, the observation, backlink edge, and alert unique keys prevent duplicates. The system is deliberately at-least-once; exactly-once network execution is not realistic at scale.
Step 9 — Handle Missing Links vs Fetch Failures Differently

A successful page fetch where the expected link is absent is evidence of potential loss. A timeout, DNS failure, or server error is not the same evidence.

Signal Action Retry Window
Successful page, link missing Increment consecutive_failures, schedule confirmation check 30–120 minutes with jitter
Second confirmed miss after retry window Change state to lost, set lost_at, emit backlink.lost —
Fetch / network failure Retain previous live/lost state, record error observation, retry with backoff 5 min → 24 hours (exponential)
HTTP 404/410 source page Stronger evidence but still use configured confirmation policy Configurable
Link returns after loss Change durable state to live, reset failures, increment the state version, and emit backlink.recovered —
Stable lost link (30+ days) Progressively reduce checking frequency to weekly under product policy Weekly
Critical Rule: Only complete, non-truncated fetch and parse evidence may advance consecutive_failures or create a lost transition. Network and parser failures update operational retry counters instead.
Step 10 — Finalize the Run

Workers increment pages_completed or pages_failed exactly once when a consumer reaches a terminal state. The run finalizer does not repeatedly count large job tables.

New-Backlink Discovery Flow

Verifying known source pages cannot discover every new backlink on the web. Adding 300 target URLs does not tell the system which external pages link to them. Discovery needs at least one candidate source:

Provider Import

Third-party SEO data providers. Hourly import scheduler with cursor-safe pagination and idempotent import runs.

Search Console

Google Search Console or another owner-authorized source with verified property ownership.

Proprietary Crawl Index

A shared crawl/index built by the product. Source pages are anonymous public responses shared safely across tenants.

Manual / API Upload

CSV or API upload of known referring pages. Validated, deduplicated, and queued for immediate verification.

The hourly provider scheduler creates an idempotent import_runs row. Import workers page through provider results using the stored cursor, normalize and deduplicate source and target URLs, upsert backlink candidates, record each provider/source in backlink_discoveries, and queue immediate verification by setting next_check_at to the current time. New projects should run discovery first — a verification run with no known backlink candidates should complete successfully with zero page jobs.

Alert Flow

Immediate Alerts

The observation transaction creates one alert_events row per meaningful state transition and one alert_deliveries row per configured channel/destination. Deduplication keys include the rule, backlink, event type, and state-transition version.

Provider Response Action
Permanent config / auth error Mark failed, notify administrator through an independent channel
Rate limit or temporary provider error Reschedule with exponential backoff and jitter
Timeout after uncertain webhook response Retry with a stable outbound idempotency header

The alert_events.aggregate_delivery_status is derived from child delivery rows: pending while none have finished; partial when outcomes are mixed; delivered when all required deliveries succeed; failed when all terminal deliveries fail; cancelled only when intentionally suppressed.

Digests

Daily/weekly digest builders run globally and calculate each tenant's due window in its configured timezone. A unique digest key prevents duplicate summaries during daylight-saving transitions or retries. All event times are stored in UTC.

Outbox Ownership

Each database shard owns a local transactional_outbox. The same transaction that changes backlink state inserts its versioned broker event; a publisher later sends it and marks it published. Alert delivery rows remain the durable delivery queue and are not recreated from Kafka. This gives one unambiguous path: the outbox bridges committed state to Kafka, while alert_deliveries controls email, Slack, and webhook retries.

Lease Recovery

Every minute, a recovery job finds fetch work whose lease has expired and requeues it. The same pattern applies to target_validation_jobs, page_parse_results, project match work in crawl_pages, alert_deliveries, and the transactional outbox. Always process limited ID batches — never update an unbounded number of rows at once.

UPDATE page_fetch_jobs
SET status       = 'queued',
    lease_owner  = NULL,
    leased_until = NULL,

WHERE status      = 'leased'
  AND leased_until < UTC_TIMESTAMP(6)

LIMIT 500;

Retention & Maintenance Policy

Object storage and MySQL cannot commit atomically. Use this artifact lifecycle for every compressed HTML body and link manifest:

  1. Create or claim a pending content record with a deterministic content-addressed key. Reuse is allowed only for anonymous public responses with compatible fetch profiles and encryption policy.
  2. Upload to a temporary or final key with server-side encryption.
  3. Read metadata and checksum back from storage.
  4. Mark the snapshot available only after verification.
  5. Allow parsers to consume only available objects.
  6. Have the artifact reconciler repair or delete stale pending rows and orphaned objects.
  7. On every reuse, atomically update last_referenced_at and extend retention_until with GREATEST.
  8. Delete an object only after retention_until has passed and no retained fetch, parse, observation, legal-hold, or export reference remains.

Hot observations (MySQL) 7–30 days, then archive to ClickHouse before deletion
ClickHouse observation history Tenant-contract retention; deletion tombstones and completion reconciliation are required
Raw HTML bodies (object storage) 7–30 days; compressed with Zstandard
Parsed link manifests Longer than HTML when useful for parser re-runs
Failed job runs Keep longer than successful audit rows
Scheduler audit rows Purge after weekly cleanup job

Major Failure Scenarios & Responses

The following scenarios cover the most critical edge cases at 100M scale. Each has a defined system response that preserves correctness without violating host rate limits or producing false link-loss events.

Shard project state by tenant/project and apply weighted fairness. Shared fetches are anonymous public responses. One tenant's jobs, queries, imports, or exports cannot consume all shard or worker capacity.

A simple tenant-only shard key creates a hotspot. Subshard that tenant by project or stable edge bucket. Send large exports to ClickHouse/object storage instead of querying all transactional shards synchronously.

Use a project plus edge-bucket routing key. All full-project counts come from rollups — never scatter-count raw rows interactively. List queries include the relevant bucket plan or use a merge service over bounded shard cursors.

Per-host politeness makes the weekly SLA infeasible at low permitted rates. Calculate projected completion continuously, prioritize valuable/change-prone pages, reduce low-value checks under explicit policy, and show limited coverage. Never evade host rate limits.

A target gains millions of candidate backlinks in hours. Deduplicate before queueing, cap admission by tenant budget, verify in priority tiers, and keep provider discovery separate from verified live state.

Use provider discovery keys and import-run idempotency. Update last_discovered_at without recreating current edges, subscriptions, or verification jobs.

Network failures never mean "lost." Open a domain-level incident, suppress link-loss transitions, extend retries with jitter, and avoid an alert storm.

Require complete evidence and confirmation policy, then aggregate notifications into digests/incidents. Apply alert fan-out budgets rather than sending millions of individual emails.

Pin parser version in every manifest and observation. Stop affected consumers, deploy a fixed parser, and reparse retained HTML offline. Emit corrected state events with higher versions — do not refetch unnecessarily.

Create a new normalization version. Dual-read/dual-resolve during backfill, produce identity-remap events, merge only after collision and ownership verification, then retire the old version. Never rewrite 100 million identities in place.

HTTP parsing remains the default. Browser rendering is a separately budgeted tier triggered by policy or heuristics. Cache rendered snapshots and cap render time, memory, scripts, and network destinations.

Apply normalization rules, query-parameter policies, per-domain URL cardinality limits, path-depth limits, content fingerprinting, and crawl-frontier budgets. Quarantine domains producing explosive low-value URL variants.

Enforce compressed and expanded byte limits, ratio limits, parser CPU/memory deadlines, sandboxing, and no script execution in ordinary parsers. Mark evidence incomplete on any limit hit.

Pause parse dispatch, retain fetch job state, apply bounded retry, and exert backpressure before fetching additional bodies that cannot be stored. Do not mark links missing.

Keep transactional outbox rows until acknowledged, stop hot-history deletion, monitor per-partition lag, and scale/rebalance consumers. Ordering remains keyed by backlink — retries do not bypass a blocked edge with a newer event.

Current state continues in MySQL shards. Pause MySQL hot-history deletion when the analytics watermark falls behind. Historical dashboards expose stale-data status explicitly.

Fail over to a replica using the tested orchestration path. Consumers retry idempotently. Do not acknowledge broker events until the state transaction commits.

Throttle expensive exports, route reads to replicas when consistency allows, split the project using stable edge buckets, and move analytical queries to ClickHouse.

Write a deletion workflow record, stop new schedules, emit tombstones to every plane, delete project-shard state, remove subscriptions, expire artifacts when no references remain, and verify completion with reconciliation. Keep only legally permitted audit proof.

Apply event deduplication, per-rule cooldown, per-tenant delivery budgets, grouping, digest fallback, and incident-level notifications. Crawl correctness must not depend on notification success.

Keep project-to-home-region routing explicit. Restore/fail over control and project shards according to the recovery objective, replay broker events, and avoid active-active writes to one edge unless conflict resolution is formally designed.

Order state using monotonic state_version, not wall-clock time alone. Reject stale versions, retain event time for reporting, and synchronize infrastructure clocks.

Version cached robots decisions. On a new disallow rule, stop future fetches, set fetch health to blocked, and retain the previous availability state rather than declaring the link lost. On allow, resume through normal scheduling.

Verify artifact availability before accepting reuse. If unavailable, retry once without conditional headers and create a fresh snapshot.

After recovery, rebuild only the short rolling horizon, order work by hard deadline and value, and enforce admission limits. Do not immediately enqueue every missed slot. Record coverage debt and drain it within available host and tenant budgets.

Continue verifying already known backlinks. Pause or slow discovery imports with cursor-safe retry, expose discovery freshness separately from verification freshness, and never interpret absent provider data as lost backlinks.

Run exports asynchronously from ClickHouse into object storage, with a stable snapshot time, progress tracking, expiry, authorization recheck, and downloadable artifact. Never hold an API connection while scanning project-state shards.

Use the sharding layer's supported copy/catch-up/switch workflow, verify row counts and event watermarks, pause destructive cleanup until rollback expires, and load-test resharding before urgent capacity pressure. Keep routing keys immutable.

8. Summary & Key Takeaways

Architectural Summary Checklist

  • Fetch Coalescing: Deduplicates requests across projects for the same referring source URL.
  • Tiered Storage: MySQL for current state, ClickHouse for immutable analytics, Object Storage for compressed HTML.
  • Conditional GETs: Saves up to 70% network traffic with ETag / 304 Not Modified.
  • Reliable Alerts: Transactional outbox prevents duplicate or missed notifications.
  • Vitess Sharding: Scales from 10M to 100M edges by splitting project state from source scheduling.
  • Decoupled Auth: Opaque tenant_id keeps user identity separate from crawl data.
